Разработай техническое задание (ТЗ) на веб-приложение для учёта научной работы преподавателей со студентами (курсантами). Код приложения на этом шаге не пиши: результат — только документация.

Рабочий проект: /home/roman/src/stocktaking. ТЗ положи в doc/tz.md (папку doc/ создай), формат Markdown, язык русский.

1. Исходные материалы

Перед началом изучи проект формы /home/roman/src/forms/forms/prepod_vnok_info/ (только чтение, ничего в нём не меняй):
- docs/README.md — обзор двух версий формы (1.0 XFA и 2.0 статичная);
- docs/static-form.md, docs/data-schema-v2.json, docs/example-data-v2.json — версия 2.0 и её схема данных;
- docs/data-schema.json — схема 1.0 (для сравнения);
- src/static/extract_static.py и src/static/prepare_copy.py — извлечение JSON из заполненного PDF, проверка --check, коды выхода, назначение ID анкеты;
- examples/README.md и examples/*.pdf — 20 примеров заполненных форм, включая ошибочные;
- docs/teacher-guide-static.md — как преподаватель заполняет форму.

Основной считай форму версии 2.0 (один файл — один студент). Утверждённой версии формы нет — отметь это в ТЗ как риск и опиши, как система должна реагировать на смену версии схемы (поле schema_version).

2. Назначение системы

- Хранение информации о преподавателях, ведущих научную работу с курсантами (студентами), о самих студентах и об их совместной работе: задача, расписание, ожидаемые результаты, статус, достижения (портфолио), примечания.
- Ввод данных двумя способами:
  а) вручную через веб-интерфейс;
  б) загрузкой заранее заполненных PDF-форм prepod_vnok_info (по одной и пакетом).
- Формирование отчётов.

3. Требования к содержанию ТЗ

Структуру выбери сам (можно опираться на ГОСТ 34.602, но без формализма ради формализма). Обязательно раскрой:

- Цели, пользователи и роли (например: администратор, ответственный кафедры, преподаватель, руководство только для просмотра). Права каждой роли — таблицей.
- Модель данных: сущности (преподаватель, кафедра, студент, группа, работа/задача, расписание, достижение, загруженный документ, журнал импорта), поля, типы, связи, обязательность. Сопоставь каждое поле JSON схемы 2.0 с полем модели. Учти, что телефон и шифр группы — строки, отчество может отсутствовать, курс — текст с проверкой 1–6.
- Импорт PDF:
  - использование логики extract_static.py (переиспользование кода или вызов как библиотеки — предложи вариант и обоснуй);
  - обработка ошибок и предупреждений --check, отказ в импорте при ошибках, показ сообщений пользователю;
  - сопоставление с уже существующими записями: тот же преподаватель (ФИО + кафедра), тот же студент, повторная загрузка той же анкеты по ID — обновление или дубликат, предварительный просмотр перед сохранением;
  - хранение исходного PDF и журнала импорта.
  Пройди по всем 20 примерам из examples/ и укажи в ТЗ ожидаемое поведение системы для каждого (таблицей).
- Ручной ввод и редактирование: формы, валидация (те же правила, что у PDF-формы), история изменений.
- Отчёты: предложи конкретный перечень (например: по преподавателю, по кафедре, по курсу/группе, по статусу работ, по достижениям за период, сводная нагрузка преподавателей). Для каждого — параметры фильтрации, состав колонок, форматы выгрузки (просмотр в браузере, XLSX, PDF, CSV).
- Нефункциональные требования: Django (актуальная LTS-версия), PostgreSQL, развёртывание через Docker Compose (состав сервисов, тома для БД и загруженных файлов, переменные окружения, миграции, создание суперпользователя, резервное копирование), объём данных, производительность, безопасность и защита персональных данных (ФИО, телефоны, email студентов), журналирование.
- Интерфейс: перечень основных экранов с кратким описанием (wireframe не нужен).
- Тестирование и приёмка: критерии приёмки, использование examples/ как тестового набора.
- Этапы разработки с приоритетами (MVP и последующие).
- Открытые вопросы к заказчику — отдельным разделом. Если что-то в требованиях неясно или противоречит материалам формы, не додумывай молча: вынеси в этот раздел и предложи вариант по умолчанию.

4. Ограничения

- Только вымышленные данные в примерах ТЗ.
- Ссылки на файлы проекта формы — абсолютными путями или с указанием проекта.
- Не создавай Django-проект, docker-compose.yml и прочий код.

В конце создай doc/report-0001.md с отчётом о выполнении: какие материалы изучены, что вошло в ТЗ (кратко по разделам), принятые допущения, список открытых вопросов, найденные расхождения в документации формы. Кратко продублируй отчёт в ответе. Коммит не делай.
