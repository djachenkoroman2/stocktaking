Реализуй в системе «Учёт НИР» выгрузку всей базы данных в JSON и восстановление базы из этой выгрузки. Функция для администратора.

Зачем: систему будут дорабатывать, и при реинжиниринге структура базы может сильно измениться. Нужен полный, понятный без исходного кода снимок данных, который можно хранить долго, читать другими программами и загрузить обратно — в эту же версию системы или, через преобразование, в следующую.

Рабочий проект: /home/roman/src/stocktaking. Перед началом прочитай doc/tz.md (версия 0.2), doc/report-implementation.md, doc/admin-guide.md, doc/deployment.md, модели accounts/models.py, registry/models.py, imports/models.py, а также scripts/backup.sh и scripts/restore.sh. Проект формы /home/roman/src/forms/forms/prepod_vnok_info/ не меняй.

1. Что выгружается

- Все данные предметной области: кафедры, преподаватели, группы, студенты, работы, достижения, статусы и их история, загрузки и пакеты импорта (с извлечённым JSON и результатами проверки), выданные копии, шаблоны формы.
- История изменений django-simple-history (Historical*-таблицы) — обязательно: при реинжиниринге она нужна так же, как текущие данные.
- Учётные записи и роли: пользователи (с хешами паролей, чтобы после восстановления вход работал), назначения ролей, связь пользователя с карточкой преподавателя, токены API, журнал аудита.
- Не выгружаются: сессии, неудачные попытки входа, служебные таблицы Django (contenttypes, permissions), если без них можно восстановить данные. Если решишь иначе — объясни в отчёте.
- Файлы (исходные PDF, выданные копии, шаблоны) в JSON не встраиваются. В JSON — путь, размер и SHA-256 каждого файла. Сами файлы — опционально в том же архиве (см. п. 2). Восстановление без файлов допустимо: записи остаются, файлы помечаются отсутствующими, и это видно в отчёте о восстановлении.
- Ссылки между записями — по первичным ключам, плюс для основных сущностей человекочитаемые ключи (название кафедры, шифр группы, ID анкеты), чтобы выгрузку можно было понять и сопоставить без базы.

2. Формат

- Выбери формат и обоснуй в документации. Рассмотри как минимум: стандартный dumpdata/loaddata Django и собственный формат «таблица → список записей». Учти цель: выгрузка должна оставаться читаемой и загружаемой после изменения моделей, а формат dumpdata жёстко привязан к текущим моделям. Допустимо сочетание: собственный формат как основной, dumpdata — только если он реально что-то упрощает.
- Обязательный заголовок: версия формата выгрузки (начни с 1), версия системы (git-коммит или версия из кода), последние применённые миграции каждого приложения, дата и время, кто выгрузил, число записей по каждой таблице, контрольная сумма данных.
- Даты и время — ISO 8601 с часовым поясом, десятичные — строками, кодировка UTF-8, без экранирования кириллицы, стабильный порядок записей (по ключу), чтобы две выгрузки одной базы можно было сравнить diff'ом.
- Результат — один ZIP-архив: data.json (или по файлу на таблицу — реши сам и обоснуй), manifest.json с заголовком, при выгрузке с файлами — каталог media/. Большая база не должна целиком загружаться в память при выгрузке (ориентир — объём из ТЗ 11.4: 50 000 загрузок, 20 000 работ).
- Опиши формат в отдельном документе doc/json-format.md: структура архива, заголовок, каждая таблица и её поля с типами и смыслом, связи, перечни значений (статусы, состояния загрузок, роли). Документ должен позволять написать конвертер без чтения кода системы.

3. Восстановление

- Восстановление только в пустую базу той же схемы (после migrate). Если в базе уже есть данные предметной области — отказ с понятным сообщением. Режим замены текущих данных сделай только при явном флаге и только после автоматической резервной копии текущей базы в JSON; если считаешь такой режим лишним — не делай и объясни.
- Перед записью — полная проверка без изменения базы: целостность архива и контрольная сумма, версия формата, совпадение миграций, ссылки на несуществующие записи, уникальность, обязательные поля. Режим только проверки (--dry-run) с тем же отчётом.
- Несовпадение миграций: если выгрузка из более старой версии системы — опиши и реализуй механизм преобразования (цепочка функций «формат N → N+1» или загрузка в схему той версии с последующим migrate — выбери и обоснуй). Сейчас версия одна, но механизм должен быть готов, а в doc/json-format.md — описано, как добавлять следующую версию. Выгрузку из более новой версии — отклонять.
- Всё восстановление — в одной транзакции: при ошибке база остаётся пустой. После загрузки в PostgreSQL выставь последовательности первичных ключей, иначе новые записи будут конфликтовать.
- Восстановление не должно создавать новые записи истории и событий аудита от имени процесса восстановления, кроме одного события «Восстановление из JSON» с именем файла.
- После восстановления — отчёт: число записей по таблицам в сравнении с заголовком, файлы восстановленные, отсутствующие и с несовпавшей SHA-256.

4. Интерфейс и права

- Команды manage.py для выгрузки и восстановления — обязательно (работают в Docker: docker compose exec web python manage.py …). Опиши параметры: путь, с файлами или без, --dry-run.
- В интерфейсе: страница «Администрирование → Выгрузка в JSON» с запуском выгрузки и скачиванием архива — только суперпользователю. Большую выгрузку выполняй в фоне через существующий worker, как пакетный импорт. Восстановление через веб-интерфейс не делай: только командой, это опасная операция.
- Выгрузка содержит персональные данные студентов (контакты) и хеши паролей. Каждая выгрузка и восстановление пишутся в журнал аудита. Готовые архивы на сервере хранятся вне публичных каталогов и отдаются только через проверку прав. Предупреждение о персональных данных — на странице выгрузки и в документации.
- Существующие scripts/backup.sh и restore.sh (pg_dump) не заменяй: JSON — для переноса и реинжиниринга, pg_dump — для резервного копирования. Различие объясни в документации.

5. Проверка

- Автотесты: выгрузка → новая пустая база → восстановление → повторная выгрузка совпадает с первой (кроме заголовка с датой); на данных из 20 примеров анкет (tests/fixtures/examples), с историей изменений, возвратами, выданными копиями, мягко удалёнными и объединёнными записями. Отказ на непустой базе, на повреждённом архиве, на неверной контрольной сумме, на более новой версии формата, на битой ссылке. Восстановление без файлов. Последовательности ключей: после восстановления создаётся новая запись. Права: страница выгрузки недоступна всем, кроме суперпользователя.
- Все существующие тесты (66) должны проходить. Тесты — на SQLite и на PostgreSQL в контейнере (команда в README).
- Живая проверка в Docker Compose: выгрузить работающий стенд, поднять второй экземпляр с пустой базой (отдельное имя проекта Compose, другие порты), восстановить, убедиться, что вход, отчёты и скачивание PDF работают.
