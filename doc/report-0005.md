## 2. Смена пользователя

1. В меню с именем пользователя нажимается «Сменить пользователя». Форма отправляет POST вместе с адресом текущей страницы (`next`).
2. Сервер выполняет обычный `logout` (в журнал аудита пишется выход с признаком `switch_user`) и запоминает в новой сессии, кто вышел. Затем открывается страница входа с `?next=…`. Внешние адреса в `next` отбрасываются.
3. На странице входа видна подсказка «Вы вышли из учётной записи «…». Войдите под другой учётной записью.» Поле логина пустое.
4. Вход проходит через тот же `LoginView`, что и обычный: блокировка после `LOGIN_MAX_FAILURES` попыток, LDAP и событие `login` в аудите работают без изменений.
5. После входа открывается страница из `next`. Если новому пользователю она недоступна (`PermissionDenied` или `Http404`, потому что объекты вне области данных дают 404), открывается главная с сообщением. Проверяется только первый запрос после входа. Дальше и при обычном входе отказ показывается как раньше: 403 или 404.

Вход «под другим пользователем» без пароля (impersonation) не сделан, как и требует задача. Предложение на будущее: если такая функция понадобится, её стоит давать только суперпользователю, с отдельной записью в аудите («X вошёл как Y»), баннером «Вы работаете как Y» на всех страницах и кнопкой возврата. Действия в этом режиме должны записываться в историю от имени настоящего пользователя. Без отдельного решения заказчика я бы её не делал.

## 3. Админка Django: найденная проблема и решение

**Проблема.** Пункт «Пользователи, роли, настройки» в меню «Администрирование» показывался всем, у кого `access.is_admin`, то есть суперпользователю и пользователю с ролью «Администратор». Стандартная админка пускает только пользователей с `is_staff` и проверяет права модели. Флаг `is_staff` система нигде не выставляет. Поэтому администратор по роли видел пункт, а получал форму входа админки и не мог войти даже со своим паролем. В тестах этого не было видно: там у администратора вручную стояли `is_superuser` и `is_staff`.

**Рассмотренные варианты.**

| Вариант | Почему не выбран или выбран |
| --- | --- |
| Показывать пункт только тем, у кого `is_staff` | Администратор по роли остаётся без управления пользователями и ролями, хотя по ТЗ 3.1 это его право |
| Выставлять `is_staff` и права при назначении роли | Два источника правды (роль и флаг), их нужно синхронизировать при снятии роли, удалении и восстановлении из JSON |
| **Доступ к админке по роли** (выбран) | Один источник правды — `RoleAssignment`, как во всей системе |

**Как сделано.**

- `SystemAdminSite.has_permission` пускает активного пользователя, если `access_for(request).is_admin` (суперпользователь или роль «Администратор» с любой областью). `is_staff` больше не учитывается: пользователь с `is_staff`, но без роли в админку не попадает. Так выполняется условие «не давать доступ пользователям без роли администратора».
- `RoleAdminBackend` выдаёт администратору по роли права всех моделей (`has_perm`, `has_module_perms`). В системе права модели проверяет только админка: интерфейс и API работают через `accounts/access.py`, поэтому на остальные права это не влияет.
- Администратору по роли, который не суперпользователь, нельзя повышать себя или других до суперпользователя и менять учётные записи суперпользователей. Поэтому поля `is_superuser`, `is_staff`, «Группы» и «Права пользователя» у него только для чтения. Учётные записи суперпользователей он может только просматривать: изменение, смена пароля и удаление дают 403.
- `/admin/login/` не показывает форму входа админки. Невошедший пользователь перенаправляется на страницу входа системы с `next=/admin/…`, вошедший без прав получает 403. Так блокировка, LDAP и аудит действуют одинаково. Выход из админки и раньше вёл на страницу входа системы (`LOGOUT_REDIRECT_URL`).
- Пункт меню переименован в «Админка Django: пользователи, роли, настройки», заголовок админки — в «Учёт НИР — админка Django». `site_url = '/'`: ссылка «Открыть сайт» ведёт на главную системы. Админка открывается в той же вкладке.

## 4. Допущения

1. Роль «Администратор» с указанной кафедрой уже сейчас даёт права на всю систему (`Access.is_admin`), поэтому она даёт и доступ к админке. Ограничивать админку кафедрой я не стал: в ней нет понятия области данных.
2. Возврат на прежнюю страницу сделан только для смены пользователя. При обычном входе с `next` на недоступную страницу по-прежнему показывается 403: это понятнее, чем молча открыть главную.
3. Для пользователя без прав админка отвечает 403 после перенаправления `/admin/` → `/admin/login/`, а не сразу: так устроена стандартная обёртка `admin_view`.
4. Отдельная страница 403 не делалась. Используется ответ Django по умолчанию, как и раньше во всей системе.
5. Администратор по роли может выпускать токены API для любых пользователей, включая суперпользователей. API только читает данные, а область данных администратора и так «вся система», поэтому новых данных он так не получит. Если это нежелательно, токены можно ограничить так же, как учётные записи.

## 5. Проверка

**Автотесты.** [tests/test_switch_user_and_admin.py](../tests/test_switch_user_and_admin.py), 23 теста:

- пункт «Сменить пользователя» есть у суперпользователя, администратора по роли, ответственного, наблюдателя, преподавателя и пользователя без ролей;
- POST выходит из сессии и ведёт на вход с `next`, на странице входа есть подсказка и пустой логин; GET даёт 405 и не выходит из сессии; внешний `next` отбрасывается;
- после смены пользователя открывается доступная прежняя страница; недоступная заменяется главной с сообщением, а дальше снова действует обычный отказ; при обычном входе отказ сохраняется;
- в аудите есть выход с `switch_user` и вход нового пользователя; блокировка после неудачных попыток действует и при смене пользователя;
- суперпользователь и администратор по роли видят пункт меню и открывают `/admin/`, список пользователей и справочники; есть ссылка «Открыть сайт»;
- ответственный, наблюдатель, преподаватель, пользователь без ролей и пользователь только с `is_staff` пункт не видят, админка отвечает им 403;
- вход в админку идёт через страницу входа системы и возвращает в `/admin/`;
- администратор по роли меняет обычного пользователя, но не может выставить `is_superuser` или `is_staff`; изменение, смена пароля и удаление суперпользователя дают 403.

**Все тесты.** 105 из 105 (82 прежних и 23 новых) проходят на SQLite (`.venv/bin/pytest`) и на PostgreSQL 17 в контейнере (команда из README).

**Живая проверка.** Стенд Docker Compose, https://localhost:8443, образ приложения пересобран. Сценарий выполнен скриптом через HTTPS с cookie и CSRF, все 16 проверок прошли:

- `admin` (суперпользователь): в меню оба пункта, `/admin/` открывается;
- GET `/accounts/switch-user/` даёт 405; POST со страницы журнала аудита ведёт на вход с подсказкой;
- вход `demo_resp` (ответственный) с `next=/accounts/audit/` открывает главную с сообщением о недоступной странице; пункта админки нет; `/admin/` даёт 403;
- смена на `demo_admin` (роль «Администратор», без `is_staff`) со страницы работ возвращает на страницу работ; пункт админки есть; `/admin/` и список пользователей открываются;
- в журнале аудита стенда события `logout {"switch_user": true}` → `login` для каждой смены.

На стенде созданы тестовые пользователи `demo_admin` (роль «Администратор», все кафедры) и `demo_resp` (ответственный кафедры прикладной математики и информатики), у обоих пароль `demo-pass-2026`. Если они не нужны, удалите их в админке.

**Сборка nginx.** При живой проверке Docker Hub был недоступен: `dial tcp [2600:…]:443: connect: network is unreachable`, нет маршрута IPv6. Поэтому пересобран только образ приложения, nginx запущен из уже собранного образа. В nginx эта задача ничего не меняла. Вероятно, ошибка `apk add openssl … no such package` из прошлой сессии вызвана той же проблемой с сетью.

## 6. Что не проверено

- Вид меню на узком экране в браузере. Пункт находится в стандартном выпадающем меню Bootstrap внутри сворачиваемой навигации, как «Выйти», но визуально в браузере я его не открывал.
- Смена пользователя с входом через LDAP на настоящем каталоге. Вход идёт через тот же `LoginView` и те же backends, существующие тесты LDAP проходят.
- Для администратора по роли проверены главная админки, список и изменение пользователей и список преподавателей. Разделы токенов API и других справочников по отдельности не открывались, они работают на тех же правах (`RoleAdminBackend`).
