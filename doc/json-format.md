# Формат выгрузки базы в JSON

Описание формата архива, который создают команда `export_json` и страница «Администрирование → Выгрузка в JSON», и который читает команда `restore_json`. Документ рассчитан на того, кто пишет конвертер или анализирует данные **без исходного кода системы**. Как выгружать и восстанавливать — в [руководстве администратора](admin-guide.md#8-выгрузка-в-json-и-восстановление). Требование — [ТЗ 11.7](tz.md#117-выгрузка-базы-в-json).

Текущая версия формата — **1** (система 0.3.0). Машиночитаемое описание схемы версии 1 — [`snapshots/formats/v1.json`](../snapshots/formats/v1.json); то же описание лежит в каждом архиве (`manifest.json`, поле `schema`).

## 1. Выбор формата

Рассматривались два варианта.

| | `dumpdata` / `loaddata` Django | Собственный формат «таблица → записи» (выбран) |
| --- | --- | --- |
| Привязка к коду | Записи вида `{"model": ..., "pk": ..., "fields": ...}` загружаются только в те же модели. Переименовали поле — `loaddata` падает, преобразовать старую выгрузку нечем | Версия формата в заголовке и цепочка преобразований `N → N+1` ([раздел 8](#8-версии-формата-и-преобразование)) |
| Описание | Нет: смысл полей — только в коде | Схема с типами, ссылками и перечнями значений внутри архива и в этом документе |
| Проверка | Нет контрольных сумм; ошибка обнаруживается посреди загрузки | SHA-256 каждого файла, контрольная сумма, полная проверка до записи |
| Объём | Читает и пишет весь набор в памяти | Таблицы пишутся и читаются потоком, по записи в строке |
| Загрузка | `loaddata` тоже пишет записи «как есть» (raw), но не проверяет данные заранее и не переносит последовательности ключей и файлы | Загрузка «как есть», в одной транзакции, после полной проверки; последовательности ключей выставляются |
| Файлы (PDF) | Не переносит | Ссылки с размером и SHA-256, сами файлы — по желанию в том же архиве |

`dumpdata` ничего не упрощает: свой формат всё равно нужен ради версий и описания, а сериализация полей занимает несколько десятков строк ([`snapshots/schema.py`](../snapshots/schema.py)).

## 2. Архив

Один ZIP-файл (ZIP64, имена в UTF-8):

```
stocktaking-20261012-214404-1-media.zip
├── manifest.json                      заголовок
├── data/
│   ├── auth.user.json                 по файлу на таблицу
│   ├── registry.department.json
│   └── …                              18 таблиц, раздел 5
└── media/                             только в выгрузке «с файлами»
    ├── imports/2026/10/<uuid>.pdf     загруженные анкеты
    ├── copies/2026/10/<uuid>.pdf      выданные копии
    └── templates/<uuid>.pdf           шаблоны формы
```

По файлу на таблицу, а не один `data.json`: каждую таблицу можно прочитать, проверить и сравнить отдельно, а архив не нужно распаковывать целиком. Пути внутри `media/` — те же, что в поле `path` файловых полей (раздел [4.3](#43-файлы)).

## 3. Заголовок `manifest.json`

```json
{
  "format": "stocktaking-snapshot",
  "format_version": 1,
  "app_version": "0.3.0",
  "git_commit": null,
  "created_at": "2026-10-12T18:44:04.533006+00:00",
  "created_by": "admin",
  "database": "postgresql",
  "migrations": {"accounts": "0001_initial", "auth": "0012_alter_user_first_name_max_length",
                 "authtoken": "0004_alter_tokenproxy_options", "imports": "0001_initial", "registry": "0001_initial"},
  "tables": [
    {"name": "auth.user", "file": "data/auth.user.json", "count": 2,
     "sha256": "5052fefaa1394bb74bf54cb82ad1aee2b0883a8e1a7c76c5b8a9421208dc5150"},
    …
  ],
  "checksum": "e3e237c4002959b3b6ecdfa853d6d76aa79147ea9f4133065b0a65ad35ed7bc2",
  "media": {"included": true, "files": 26, "bytes": 7726603, "referenced": 26, "missing": 0},
  "warnings": [],
  "schema": { … }
}
```

| Поле | Смысл |
| --- | --- |
| `format` | Всегда `stocktaking-snapshot` |
| `format_version` | Версия формата данных (целое). Меняется, когда меняется состав таблиц или полей |
| `app_version` | Версия системы (`config/version.py`) |
| `git_commit` | Коммит исходного кода, если известен: из `git` или переменной окружения `APP_COMMIT`. В Docker-образе каталога `.git` нет, поэтому без `APP_COMMIT` — `null` |
| `created_at` | Время выгрузки, UTC |
| `created_by` | Кто выгрузил: имя пользователя или `manage.py` для командной строки |
| `database` | СУБД источника: `postgresql` или `sqlite` |
| `migrations` | Последняя применённая миграция Django каждого приложения, чьи таблицы выгружены. Справочно: совместимость определяет `format_version` |
| `tables` | Таблицы в порядке загрузки: имя, файл, число записей, SHA-256 файла |
| `checksum` | SHA-256 от строк `«файл»:«sha256»\n` всех таблиц по порядку. Обнаруживает повреждение; защитой от намеренной подмены не является |
| `media` | `included` — есть ли файлы в архиве; `files`, `bytes` — сколько положено в архив; `referenced` — на сколько файлов ссылаются записи; `missing` — сколько из них не было на диске при выгрузке |
| `warnings` | Предупреждения выгрузки (например, о не выгружаемых группах Django) |
| `schema` | Схема: таблица → `title` и список полей (`name`, `type`, `null`, `primary_key`, `unique`, `max_length`, `choices`, `ref`, `weak`, `title`) — как в [разделе 6](#6-таблицы-и-поля) |

## 4. Файлы таблиц

Каждый файл — JSON-массив объектов, **по одной записи на строке**:

```json
[
{"id": 1, "_key": "Кафедра прикладной математики и информатики", "name": "Кафедра прикладной математики и информатики", "short_name": "", "aliases": [], "is_active": true}
]
```

Пустая таблица — `[` и `]` на двух строках. Разметка «запись на строке» позволяет читать большие файлы построчно и сравнивать две выгрузки через `diff`; любой JSON-парсер читает файл и целиком.

- Записи упорядочены по первичному ключу, ключи объекта — в порядке полей из [раздела 6](#6-таблицы-и-поля).
- Кодировка UTF-8, кириллица не экранируется. Переводы строк внутри текста — `\n`.
- Ключи, начинающиеся с `_`, — справочные, при восстановлении не используются. Сейчас это только `_key` (раздел [4.2](#42-ссылки-и-человекочитаемые-ключи)).
- Две выгрузки одной и той же базы отличаются только полями `created_at`, `created_by` заголовка.

### 4.1. Значения

| Тип в схеме | В JSON | Пример |
| --- | --- | --- |
| `integer` | число | `14` |
| `string` | строка; пустое значение — `""`, не `null` | `"Иванов"` |
| `boolean` | `true` / `false` | `true` |
| `date` | строка ISO 8601 | `"2026-09-15"` |
| `datetime` | строка ISO 8601 в UTC со смещением | `"2026-10-12T18:44:04.533006+00:00"` |
| `json` | значение как есть: объект, массив, строка, число | `{"student": {…}}` |
| `ref` | первичный ключ записи другой таблицы или `null` | `5` |
| `file` | объект файла или `null` | раздел [4.3](#43-файлы) |
| `decimal` | строка (сейчас таких полей нет) | `"12.50"` |

`null` допустим только у полей, где в схеме `"null": true`, и у файловых полей.

### 4.2. Ссылки и человекочитаемые ключи

Ссылка — значение первичного ключа (`id`) записи в таблице из `ref`; в имени поля нет суффикса `_id`. Например, `"teacher": 5` в `registry.researchwork` — запись с `"id": 5` в `registry.teacher`.

Ссылки с пометкой `weak` (без ограничения) есть только в таблицах истории: они указывают, к какой записи относилась версия, и могут ссылаться на запись, которую позже удалили.

Чтобы выгрузку можно было понять без базы, у основных сущностей есть поле `_key` — устойчивое человекочитаемое обозначение записи (кафедра — название, группа — шифр, преподаватель — «ФИО / кафедра», работа — ID анкеты). Сопоставляйте записи разных выгрузок или систем по `_key` и уникальным полям, а не по `id`: ключи `id` в другой базе будут другими.

### 4.3. Файлы

Значение файлового поля:

```json
{"path": "copies/2026/10/38b1a29df4bb4db18cfd1db4edda8d0d.pdf", "size": 291535,
 "sha256": "591b2a2d88808c56dd44bea94f76011322f5d727a1f0411153ee2142c16cea58"}
```

- `path` — путь внутри хранилища файлов (`MEDIA_ROOT`) и внутри каталога `media/` архива.
- `size`, `sha256` — размер в байтах и SHA-256 файла на момент выгрузки. Если файла на диске не было, оба `null`.
- `null` вместо объекта — у записи нет файла: не загружался или удалён командой `purge_pdfs` (у загрузок PDF тогда заполнено `file_purged_at`).

У `imports.importeddocument` есть и собственное поле `sha256` — SHA-256 загруженного PDF, по которому система находит дубликаты. Оно не зависит от выгрузки.

## 5. Состав

### 5.1. Таблицы и связи

Порядок — порядок загрузки (сначала те, на которые ссылаются):

```
auth.user ◄──────────────── почти все таблицы (кто создал, загрузил, вернул, выдал…)
  └─ authtoken.token
registry.department ◄─ studygroup ◄─ student ◄──┐
         ▲                                       │
         └──────────── teacher ◄──────────── researchwork ◄─ achievement
accounts.roleassignment → user, department
accounts.auditevent → user
imports.formtemplate ◄─ issuedcopy → teacher, student, researchwork, importeddocument
imports.importbatch ◄─ importeddocument → department, researchwork, importeddocument (дубликат, повторная)
registry.historical* — версии teacher, student, researchwork, achievement
```

Ссылки внутри одной таблицы: `teacher.merged_into`, `student.merged_into` (объединённые дубликаты), `importeddocument.duplicate_of` и `resubmission`.

### 5.2. Что не выгружается

| Таблица Django | Почему |
| --- | --- |
| `auth.group`, права пользователей | Не используются: права системы задаются ролями (`accounts.roleassignment`). Если группы или отдельные права всё же есть, выгрузка предупреждает |
| `auth.permission`, `contenttypes.contenttype` | Служебные, создаются командой `migrate` |
| `admin.logentry` | Журнал админ-панели Django; значимые действия записываются в журнал аудита |
| `sessions.session` | Сеансы входа |
| `accounts.loginfailure` | Временные данные блокировки входа |
| `snapshots.snapshotexport` | Журнал самих выгрузок; архивы на сервере не переносятся |
| Файлы `media`, на которые нет ссылок | Не нужны системе |

### 5.3. Персональные данные

Архив содержит ФИО, телефоны и адреса почты студентов (`registry.student`, `registry.historicalstudent`, извлечённые данные анкет `imports.importeddocument.extracted`, сами PDF), а также хеши паролей (`auth.user.password`) и ключи API (`authtoken.token.key`). Ключ API — действующий пароль к API. Обращайтесь с архивом как с резервной копией базы.

### Таблицы истории

`registry.historicalteacher`, `registry.historicalstudent`, `registry.historicalresearchwork`, `registry.historicalachievement` — версии записей, которые ведёт `django-simple-history`: по записи на каждое создание, изменение и удаление. Поля:

- все поля исходной таблицы с теми же именами и типами, в том числе `id` — ключ исходной записи. Уникальность и ссылки не проверяются: ссылки — `weak`, а `id` повторяется в каждой версии;
- `history_id` — ключ версии;
- `history_date` — время изменения;
- `history_type` — `+` создание, `~` изменение, `-` удаление;
- `history_change_reason` — причина, например «Загрузка PDF №12», или `null`;
- `history_user` → `auth.user` — кто изменил, или `null`.

Текущее состояние записи — её последняя по `history_date` версия; удалённые записи есть только в истории.

## 7. Проверки при восстановлении

`restore_json` ничего не пишет в базу, пока не пройдены все проверки (их же выполняет `--dry-run`):

1. Архив открывается, есть `manifest.json` с `format = stocktaking-snapshot`; имена внутри архива без `..` и абсолютных путей.
2. Версия формата не новее поддерживаемой; для более старой есть цепочка преобразований.
3. Контрольная сумма и SHA-256 каждого файла таблицы совпадают с заголовком; число записей совпадает с `count`.
4. В базе применены все миграции; таблицы предметной области пусты; пользователей нет, или задан `--drop-existing-users`.
5. Каждая запись: набор полей совпадает со схемой текущей версии; типы и даты читаются; обязательные поля не `null`; строки не длиннее `max_length`; ключи и уникальные значения не повторяются (шифр группы и название кафедры — без учёта регистра); ссылки ведут на существующие записи.
6. Файлы: путь не выходит за пределы `MEDIA_ROOT`; файл из архива не затирает другой файл с тем же путём.

Не являются ошибками и выводятся предупреждениями: значение вне перечня, пустая строка в поле, которое обязательно в формах, несовпадение SHA-256 файла, отсутствующий файл.

После проверки все таблицы загружаются в одной транзакции (ошибка — база остаётся пустой), последовательности первичных ключей выставляются по максимальным значениям, файлы распаковываются в `MEDIA_ROOT`, и в журнал аудита записывается одно событие `json_restore`. Записи вставляются без вызова логики моделей: история изменений, даты `created_at`/`updated_at` и автор изменений переносятся без искажений, а записей истории «от восстановления» не появляется.

## 8. Версии формата и преобразование

`format_version` описывает состав таблиц и полей. Пока он не менялся, выгрузка загружается в любую версию системы с тем же форматом, даже если миграции различаются (поля всё равно сверяются со схемой; различие миграций — предупреждение). Выгрузка из более новой версии формата отклоняется.

Для старых версий восстановление пропускает данные через цепочку преобразований `UPGRADES[N]: N → N+1` из [`snapshots/upgrades.py`](../snapshots/upgrades.py): по таблице, потоком записей. Другой вариант — восстановить старую выгрузку в старую версию системы и обновить её миграциями — отвергнут: для него нужен работающий старый код, а цель выгрузки — пережить переработку системы.

### Как выпустить новую версию формата

Тест `test_schema_matches_saved_format` падает, как только модель меняется так, что меняется схема (поле добавлено, удалено, переименовано, сменились тип, `null`, длина, перечень значений). Тогда:

1. Поднять `FORMAT_VERSION` в [`snapshots/schema.py`](../snapshots/schema.py).
2. Сохранить схему новой версии рядом с прежними: `python manage.py shell -c "import json; from snapshots import schema; open('snapshots/formats/v2.json', 'w').write(json.dumps(schema.describe(), ensure_ascii=False, indent=2) + '\n')"`. Старые файлы `v1.json`… не удалять — это описание форматов уже сделанных выгрузок.
3. Новая модель — добавить её в `TABLES` (порядок загрузки) или в `EXCLUDED` с причиной.
4. Написать преобразование `v1_to_v2(table, records)` и зарегистрировать `UPGRADES = {1: v1_to_v2}`: переименование таблицы, поля, значение по умолчанию для нового обязательного поля, перекодировка перечня. Пример — в документации модуля.
5. Тест: старая выгрузка (можно получить, изменив архив, как в `test_upgrade_from_older_format`) восстанавливается в новую версию.
6. Обновить этот документ: версию, [раздел 6](#6-таблицы-и-поля), список изменений ниже.

Ограничение: преобразование работает с одной таблицей за раз. Если новая таблица заполняется из нескольких старых, оставьте её пустой при восстановлении и заполните миграцией данных Django после него.

## 9. Чтение без системы

Пример на Python без Django: работы с ФИО студента и преподавателя.

```python
import json, zipfile

with zipfile.ZipFile('stocktaking-20261012-214404-1.zip') as archive:
    manifest = json.loads(archive.read('manifest.json'))
    assert manifest['format'] == 'stocktaking-snapshot' and manifest['format_version'] == 1
    table = lambda name: json.loads(archive.read(f'data/{name}.json'))
    teachers = {t['id']: t['_key'] for t in table('registry.teacher')}
    students = {s['id']: s['_key'] for s in table('registry.student')}
    for work in table('registry.researchwork'):
        if not work['is_deleted']:
            print(work['questionnaire_id'], work['status'], students[work['student']], teachers[work['teacher']])
```

Для больших таблиц читайте файл построчно: первая строка `[`, последняя `]`, остальные — по записи, с запятой в конце у всех, кроме последней.
