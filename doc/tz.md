## 1. Общие сведения

### 1.1. Предмет

Веб-приложение на Django для учёта научной работы, которую преподаватели ведут со студентами (курсантами). Хранит сведения о преподавателях, студентах, поставленных задачах, расписании работы, ходе выполнения и достижениях. Формирует отчёты.

Данные поступают двумя путями:

- ручной ввод через веб-интерфейс;
- загрузка заполненных PDF-форм `prepod_vnok_info` «Информация о студенте (курсанте)».

Далее в тексте «студент» означает «студент (курсант)», если не сказано иное.

### 1.2. Связанные материалы

Проект формы: `/home/roman/src/forms/forms/prepod_vnok_info/`. Пути ниже даны относительно него.

## 2. Цели и назначение

1. Хранить в одной базе данных сведения о научной работе преподавателей со студентами вместо разрозненных PDF и таблиц.
2. Убрать ручной перенос данных из PDF-форм: данные извлекаются автоматически, человек только проверяет и подтверждает.
3. Получать отчёты по преподавателям, кафедрам, курсам, группам, статусам и достижениям за выбранный период.
4. Отслеживать сбор анкет: кому выданы копии формы, какие вернулись, какие отклонены и почему.
5. Хранить исходные PDF и историю изменений, чтобы любое значение можно было проследить до источника.

Вне рамок системы (на текущем этапе): учебная нагрузка и расписание вуза, электронный журнал, учёт публикаций в наукометрических базах, интеграция с внешними информационными системами (см. [вопрос 12](#142-открытые-вопросы)).

## 3. Пользователи и роли

| Роль | Кто | Область данных |
| --- | --- | --- |
| Администратор | Технический специалист | Вся система, кроме контактов студентов |
| Ответственный кафедры | Сотрудник кафедры, собирающий анкеты | Назначенные ему кафедры |
| Преподаватель | Научный руководитель студентов | Только свои работы, только просмотр |
| Наблюдатель | Руководство: заведующий кафедрой, декан, отдел НИР | Назначенные кафедры или вся система; только просмотр и отчёты |

Пользователь может иметь несколько ролей; права складываются. Учётная запись с ролью «Преподаватель» связывается с записью преподавателя в справочнике.

Данные в систему вносят только ответственные (и администратор). Преподаватель передаёт данные через PDF-анкету, а в системе только смотрит свои работы. Это допущение версии 0.2: если преподаватель вносит в анкету данные, а ответственный загружает её, ручное редактирование преподавателем дублирует этот путь. Кроме того, телефон и email студента обязательны, а преподаватель их не видит ([вопрос 17](#142-открытые-вопросы)).

### 3.2. Где скрываются контакты

Пользователь без роли ответственного не видит телефон и email студента нигде:

- в карточке и списках студентов, в карточке работы — полей нет;
- в поиске — поиск по телефону и email не выполняется;
- в предпросмотре импорта и журнале импорта — значения заменены на «скрыто» (администратор может импортировать, но контактов не видит);
- в истории изменений — изменения этих полей показываются как «изменено» без значений;
- во всех отчётах, кроме отчёта 7, контактов нет; отчёт 7 и выгрузки с контактами доступны только ответственным;
- в API — полей нет;
- заполненные исходные PDF скачивают только ответственные. Выданные копии формы контактов студента не содержат, их скачивают ответственный и администратор;
- в стандартной админ-панели Django полей контактов нет.

Исключение — полная выгрузка базы в JSON ([11.7](#117-выгрузка-базы-в-json)): это снимок всех данных для переноса, контакты в нём есть. Её делает только суперпользователь — тот же круг лиц, что имеет доступ к базе и резервным копиям ([вопрос 21](#142-открытые-вопросы)).

## 4. Исходная PDF-форма

### 4.1. Версии

| Версия | Технология | Студентов в файле | Схема JSON | Поддержка в системе |
| --- | --- | --- | --- | --- |
| 2.0 (draft02 и новее) | AcroForm, без XFA | Один | 2.0 | **Основная** |
| 2.0-draft01 | AcroForm | Один | 1.0 | Анкета возвращается преподавателю с сообщением, как в `extract_static.py` |
| 1.0 | Динамическая XFA | Любое число | 1.0 | Не поддерживается (решение 1 в [14.1](#141-принятые-решения)); анкета возвращается преподавателю для заполнения формы 2.0 |

**Утверждённой версии формы нет** (статус «черновик», текущий файл `output/drafts/prepod_vnok_info-v2.0-draft04.pdf`). Это риск ([раздел 15](#15-риски)): состав полей может измениться. Поэтому:

- импорт строится на адаптерах: один адаптер на пару (`form_id`, `schema_version`). Адаптер превращает данные формы в нейтральную структуру импорта ([7.3](#73-архитектура-импорта)). Новая версия схемы — новый адаптер и, при необходимости, миграция модели. Существующие адаптеры не меняются;
- файл с неизвестной (более новой) версией схемы получает состояние «Версия не поддерживается» с сообщением «Версия схемы данных X не поддерживается» и сохраняется в журнале импорта. После добавления адаптера такие файлы можно обработать повторно из журнала;
- извлечённый JSON сохраняется целиком при каждой загрузке. Это позволяет повторно обработать данные, если правила сопоставления изменятся;
- в записи загрузки хранятся `form_id`, `schema_version` и SHA-256 файла.

### 4.2. Состав данных схемы 2.0

Одна анкета содержит: дату заполнения; ФИО, должность и кафедру преподавателя одной строкой каждое; фамилию, имя, отчество, курс, шифр группы, телефон и email студента; расписание (свободный текст); задачу; ожидаемые результаты; текущий статус (свободный текст); до 10 достижений; примечание. Служебные поля: `form_id`, `schema_version`, ID анкеты.

Обязательные для завершения поля: фамилия, имя, шифр группы, телефон, email, задача. Значения в форме не преобразуются: телефон и шифр группы — строки с `+`, ведущими нулями, буквами и разделителями.

## 5. Модель данных

### 5.1. Сущности

```text
Кафедра 1──* Преподаватель 1──* Работа *──1 Студент *──1 Группа
                                  │
                                  ├──* Достижение
                                  ├──* Загрузка PDF *──1 Пакет импорта
                                  └──0..1 Выданная копия
```

Расписание в схеме 2.0 — одна строка свободного текста. Поэтому в модели это текстовое поле работы, а не отдельная сущность. Структурированное расписание (дни, время, аудитория) — возможное развитие, если оно появится в форме ([вопрос 6](#142-открытые-вопросы)).

Ниже «обяз.» означает, что поле обязательно при сохранении в системе. Все текстовые поля хранятся как введены, кроме обрезки пробелов по краям ([5.3](#53-правила-хранения-значений)).

#### Кафедра (`Department`)

| Поле | Тип | Обяз. | Примечание |
| --- | --- | --- | --- |
| `name` | Строка до 255 | Да | Уникально без учёта регистра. Пример: «Кафедра прикладной математики и информатики» |
| `short_name` | Строка до 50 | Нет | Для отчётов: «ПМИ» |
| `aliases` | Список строк | Нет | Другие написания из анкет. Используются при сопоставлении |
| `is_active` | Логическое | Да | Неактивные скрыты из списков выбора |

#### Преподаватель (`Teacher`)

| Поле | Тип | Обяз. | Примечание |
| --- | --- | --- | --- |
| `last_name`, `first_name`, `middle_name` | Строки до 100 | Фамилия и имя — да | Из анкеты приходит одна строка ФИО; разбор — в [7.5](#75-сопоставление-с-существующими-записями) |
| `position` | Строка до 255 | Нет | Свободный текст. В анкетах встречаются должность вместе со степенью и званием: «Профессор, доктор технических наук» |
| `academic_degree`, `academic_title` | Строки до 100 | Нет | Заполняются вручную, из анкеты не разбираются ([вопрос 7](#142-открытые-вопросы)) |
| `department` | Ссылка на кафедру | Да | Основная кафедра |
| `email`, `phone` | Строки | Нет | Контакты преподавателя |
| `user` | Ссылка на пользователя | Нет | Для роли «Преподаватель» |
| `is_active` | Логическое | Да | |

#### Группа (`StudyGroup`)

| Поле | Тип | Обяз. | Примечание |
| --- | --- | --- | --- |
| `code` | Строка до 50 | Да | Шифр как в анкете: «ПМИ-31», «007-ПМИ/01». Уникален без учёта регистра |
| `department` | Ссылка на кафедру | Нет | Выпускающая кафедра, если известна |
| `is_active` | Логическое | Да | |

#### Студент (`Student`)

| Поле | Тип | Обяз. | Примечание |
| --- | --- | --- | --- |
| `last_name`, `first_name` | Строки до 100 | Да | Имя может состоять из нескольких слов: «Ван Тхань» |
| `middle_name` | Строка до 100 | Нет | Может отсутствовать |
| `category` | Выбор: студент / курсант | Нет | В форме не указывается; по умолчанию не задано |
| `course` | Целое 1–6 | Нет | Текущий курс. Значение вне диапазона не сохраняется в это поле ([7.4](#74-проверки-и-реакция-на-них)) |
| `group` | Ссылка на группу | Да | |
| `phone` | Строка до 50 | Да | Без маски и преобразований |
| `email` | Строка до 254 | Да | Проверка формата как в `extract_static.py`: `^[^\s@]+@[^\s@]+\.[^\s@]+$` |
| `is_active` | Логическое | Да | Выпуск или отчисление — `false`, записи сохраняются |

#### Работа (`ResearchWork`)

| Поле | Тип | Обяз. | Примечание |
| --- | --- | --- | --- |
| `questionnaire_id` | Строка до 100 | Нет | ID анкеты из PDF. Уникален, если задан. У работы, созданной вручную, пуст до выдачи копии |
| `teacher` | Ссылка на преподавателя | Да | |
| `student` | Ссылка на студента | Да | |
| `task` | Текст без ограничения длины | Да | Задача, поставленная преподавателем |
| `schedule` | Текст | Нет | Расписание работы, свободный текст |
| `expected_results` | Текст | Нет | |
| `status` | Выбор | Да | Статус работы из фиксированного списка ([5.4](#54-статусы-работы)). По умолчанию «В работе» |
| `status_comment` | Строка до 500 | Нет | Комментарий к статусу. При импорте — текст поля «Текущий статус» из анкеты как есть: «Решено 8 задач из 20» |
| `course_at_filling` | Строка до 20 | Нет | Курс, как он указан в последней анкете: «3», «II». Нужен, потому что курс студента меняется с годами |
| `date_filled` | Дата | Нет | Дата заполнения из последней загруженной анкеты; при ручном вводе — дата сохранения |

Одной паре «преподаватель — студент» может соответствовать несколько работ: разные учебные годы или разные задачи. Система предупреждает при создании второй активной работы для той же пары в том же учебном году, но не запрещает это.

### 5.3. Правила хранения значений

- Пробелы по краям однострочных полей обрезаются при сохранении в модель; в `ImportedDocument.extracted` остаётся исходное значение. Значение из одних пробелов считается пустым (пример 18).
- Внутренние пробелы, регистр, буквы `ё`/`Ё`, типографские символы (`«»`, `—`, `№`, `’`, неразрывный пробел) сохраняются. При поиске совпадений используется нормализованная форма: регистр не учитывается, `ё` = `е`, повторные пробелы сжимаются, неразрывный пробел = пробел.
- Переводы строк в многострочных полях — `\n` (извлечение приводит `\r` и `\r\n`).
- Телефон и шифр группы не преобразуются в числа и не приводятся к маске.
- Длина многострочных полей не ограничивается: форма позволяет ввести больше, чем видно на печати (пример 14), и система хранит текст полностью.
- `null` в JSON не используется; пустое необязательное поле в модели — пустая строка (текст) или `NULL` (дата, число, ссылка).

### 5.4. Статусы работы

Фиксированный список вместо свободного текста (решение 3 в [14.1](#141-принятые-решения)).

| Код | Статус | Когда ставится | Допустимые переходы | Активная |
| --- | --- | --- | --- | --- |
| `planned` | Планируется | Тема и задача согласованы, к выполнению не приступили | В работе, Прекращена | Да |
| `in_progress` | В работе | Студент выполняет задачу | Приостановлена, Завершена, Прекращена | Да |
| `suspended` | Приостановлена | Работа временно не ведётся: академический отпуск, служебная командировка, ожидание ресурсов | В работе, Прекращена | Да |
| `completed` | Завершена | Получен ожидаемый результат | В работе (возобновление) | Нет |
| `terminated` | Прекращена | Работа закончена без ожидаемого результата: отчисление, смена темы или руководителя, отказ студента | В работе (возобновление) | Нет |

- «Активные» работы — `planned`, `in_progress`, `suspended`. Они считаются в отчётах о нагрузке и о числе активных студентов.
- Новая работа получает статус «В работе», если ответственный не выбрал другой.
- Переход вне таблицы система не выполняет и сообщает, какие переходы допустимы. Возобновление (из «Завершена» или «Прекращена») требует комментария.
- Каждая смена статуса записывается в историю: кто, когда, старый и новый статус.
- В форме 2.0 поле «Текущий статус» — свободный текст. Его значение сохраняется в `status_comment`, а статус из списка выбирает ответственный в предпросмотре. Заменить текстовое поле списком с этими значениями можно в следующей версии формы ([вопрос 18](#142-открытые-вопросы)).

## 6. Ручной ввод и редактирование

### 6.1. Функции

Ручной ввод выполняют ответственный и администратор в пределах прав ([3.1](#31-права)). Преподаватель данные не вводит: изменения он вносит в свою PDF-анкету.

- Создание, изменение, деактивация кафедр, групп, преподавателей, студентов.
- Смена статуса работы по правилам [5.4](#54-статусы-работы).
- Создание работы: выбор преподавателя и студента из справочников с поиском или создание студента прямо из формы работы.
- Редактирование всех полей работы, добавление, изменение, удаление и сортировка достижений. Ограничения на 10 достижений нет: оно есть только у PDF-формы.
- Удаление работы — мягкое (пометка), с возможностью восстановления администратором. Физическое удаление — только администратором, с подтверждением, вместе с загрузками PDF.
- Объединение дубликатов преподавателей и студентов (ответственный, администратор): выбрать основную запись, перенести на неё работы, вторую деактивировать. Действие записывается в историю.

### 6.2. Проверки

Те же правила, что у `extract_static.py --check`, плюс проверки модели:

| Поле | Правило | Тип |
| --- | --- | --- |
| Фамилия, имя студента, шифр группы, телефон, email, задача | Не пусто после обрезки пробелов | Ошибка, сохранить нельзя |
| Email | `^[^\s@]+@[^\s@]+\.[^\s@]+$` после обрезки пробелов | Ошибка |
| Дата заполнения | Существующая дата; в интерфейсе — выбор даты | Ошибка |
| Курс | Целое 1–6 или пусто | Ошибка в поле `Student.course` (поле числовое) |
| Преподаватель, кафедра | Выбраны из справочника | Ошибка |
| Вторая активная работа той же пары в том же учебном году | — | Предупреждение, сохранить можно |
| Студент с теми же ФИО и группой или тем же email уже есть | — | Предупреждение с предложением выбрать существующего |

Сообщения показываются у полей и сверху формы. Тексты сообщений совпадают с текстами `extract_static.py`, чтобы пользователь видел одинаковые формулировки при ручном вводе и импорте.

### 6.3. История

На странице работы, студента и преподавателя — вкладка «История»: список изменений с автором, датой, источником и разницей значений.

## 7. Импорт PDF-форм

### 7.1. Сценарий

Импорт выполняют только ответственные кафедры и администратор (решение 2 в [14.1](#141-принятые-решения)).

1. Ответственный выбирает один или несколько PDF или ZIP-архив с PDF. Ограничения по умолчанию: 10 МБ на файл, 200 файлов и 200 МБ на пакет (настраиваются).
2. Система для каждого файла: сохраняет его, считает SHA-256, извлекает данные, выполняет проверки, ищет совпадения.
3. Ответственный видит сводку пакета: сколько готово к сохранению, сколько требует решения, сколько нужно вернуть преподавателю, сколько отклонено.
4. Анкеты с ошибками проверки сразу получают состояние «К возврату» и не сохраняются ([7.7](#77-возврат-анкеты-преподавателю)). Исправлять в системе значения с ошибками нельзя (решение 4 в [14.1](#141-принятые-решения)).
5. Для остальных файлов открывается **предпросмотр**: извлечённые значения, предупреждения у полей, найденные совпадения, при повторной загрузке — разница со старыми значениями. В предпросмотре ответственный принимает решения, которые не меняют данные анкеты: выбирает статус работы ([5.4](#54-статусы-работы)), преподавателя и кафедру, студента из найденных, курс при предупреждении, какие значения принять при повторной загрузке.
6. Ответственный подтверждает или отклоняет файл. Файлы без предупреждений и неоднозначностей («Готово») можно подтвердить все сразу кнопкой «Сохранить все готовые». Новая работа при этом получает статус «В работе», обновляемая сохраняет текущий статус.
7. После каждого подтверждения сопоставление остальных файлов пакета повторяется: преподаватель и кафедра, созданные при подтверждении одного файла, находятся для следующих. Поэтому в пакете с новыми справочными записями решение нужно принять один раз, а не для каждого файла.
8. Без подтверждения ничего не записывается в рабочие таблицы: работы, студенты, преподаватели не меняются. Неподтверждённые загрузки остаются в журнале в состоянии «Ожидает решения».

Для пакета больше 20 файлов обработка выполняется в фоне с индикатором прогресса; ответственный может закрыть страницу и вернуться к пакету позже.

### 7.2. Состояния загрузки

| Состояние | Когда | Что дальше |
| --- | --- | --- |
| В очереди | Файл ждёт фоновой обработки | Обрабатывается автоматически |
| Ожидает решения | Извлечение и проверка прошли, нужен предпросмотр | Подтвердить или отклонить |
| Готово (вид «Ожидает решения») | Нет предупреждений и неоднозначностей | Можно сохранить без открытия предпросмотра |
| Сохранено | Подтверждено, данные записаны | Ссылка на работу |
| К возврату | Ошибки проверки, нет ID анкеты, анкета в старой версии формы | Ответственный передаёт преподавателю текст возврата и отмечает возврат |
| Возвращено преподавателю | Ответственный отметил, что передал текст | Ждём исправленную анкету; при её загрузке ставится связь `resubmission` |
| Версия не поддерживается | Форма `prepod_vnok_info` с неизвестной версией схемы | Переобработать после обновления системы |
| Отклонено проверкой | Не PDF, повреждённый PDF, PDF без полей, другая форма | Исправить нельзя; можно удалить из журнала |
| Отклонено пользователем | Ответственный отказался сохранять | Комментарий обязателен |
| Дубликат файла | Файл с тем же SHA-256 уже загружен и не отклонён пользователем | Ссылка на предыдущую загрузку; ничего не записывается |

### 7.3. Архитектура импорта

**Переиспользование `extract_static.py`.** Варианты:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| А. Вызов как внешней программы (`subprocess`) | Код формы не трогается | Разбор stdout/stderr, коды выхода, накладные расходы на процесс, сложнее тесты |
| Б. Копия модулей в приложение и вызов функций | Прямой вызов `extract_data()` и `check()`, данные и сообщения — объекты Python | Копию нужно обновлять при изменении формы |
| В. Отдельный пакет Python из проекта форм | Один источник кода, версия фиксируется в зависимостях | Нужно оформить пакет в проекте форм (`pyproject.toml`), сейчас его нет |

**Рекомендация: вариант Б, переход на В, когда форма будет утверждена.**

- `src/static/extract_static.py`, `src/static/acroform.py` и `src/static/prepare_copy.py` копируются в модуль адаптера `imports/adapters/prepod_vnok_info_v2/vendor/` без изменений. В `README` модуля записываются исходный путь, дата копирования и SHA-256 каждого файла.
- Адаптер вызывает `read_fields()`/`extract_data()` и `check()` как функции. `extract_data()` принимает путь, поэтому файл из хранилища передаётся по пути на диске. Исключения `ValueError` — ошибки извлечения (аналог кода выхода 1).
- `acroform.py` импортирует `fontTools` на уровне модуля, поэтому `fonttools` нужен в зависимостях приложения. Версии `pypdf` и `fonttools` фиксируются такими же, как в `src/requirements.txt` проекта форм (`pypdf==6.19.0`, `fonttools==4.60.1`).
- Тест «паритет с формой» прогоняет копию модулей на 20 примерах `examples/` и сверяет результат с таблицей ожиданий из `examples/README.md` ([раздел 12](#12-тестирование-и-приёмка)). Если в проекте форм изменится извлечение, тест покажет расхождение после обновления копии.
- `--assign-id` и временные ID не используются: анкета без ID возвращается преподавателю ([7.7](#77-возврат-анкеты-преподавателю)).

Цепочка обработки:

```text
PDF → хранилище (SHA-256) → определение формы и версии → адаптер: extract_data() + check()
    → ошибки? → К возврату
    → нейтральная структура → сопоставление → предпросмотр → подтверждение → запись в модель
```

Нейтральная структура импорта не зависит от версии формы: данные преподавателя, студента, работы и список достижений с номерами строк. Сопоставление, предпросмотр и запись работают только с ней.

### 7.4. Проверки и реакция на них

| Ситуация | Источник | Реакция системы |
| --- | --- | --- |
| Не PDF, повреждённый PDF, PDF без полей (например, получен «печатью в PDF») | Ошибка извлечения | Отклонено проверкой. Сообщение: «В PDF нет полей формы (возможно, он получен печатью в PDF)». Если по имени файла понятно, от кого он, ответственный сам сообщает преподавателю |
| Другая форма (иной `form_id`) | Ошибка извлечения | Отклонено проверкой |
| XFA-версия 1.0, черновик draft01 (схема 1.0) | Ошибка извлечения | К возврату: заполнить анкету в форме 2.0 |
| Неизвестная версия схемы формы `prepod_vnok_info` | Ошибка извлечения | Версия не поддерживается |
| Нет ID анкеты (пример 20) | Ошибка извлечения | К возврату. В тексте возврата — просьба перенести данные в новую копию; ответственный готовит копию в системе ([8](#8-подготовка-копий-формы)) кнопкой из карточки загрузки |
| Не заполнено обязательное поле, неверный email, неверная или несуществующая дата | Ошибка `check()` | К возврату со списком ошибок |
| Курс не целое 1–6 (`II`, `1 курс`, `0`) | Предупреждение `check()` | Ожидает решения. Система предлагает значение: римская цифра или число в начале строки (`II` → 2, `1 курс` → 1); ответственный подтверждает или очищает. Исходный текст сохраняется в `course_at_filling` |
| Пустой блок преподавателя (пример 02) | Система | Ожидает решения: преподаватель берётся из выданной копии ([8](#8-подготовка-копий-формы)), иначе ответственный выбирает его вручную |
| Преподаватель или кафедра не найдены | Система | Ожидает решения: предложение создать запись (с разбором ФИО) или выбрать существующую |
| Группа не найдена | Система | Не требует решения: группа создаётся при сохранении, в предпросмотре отмечена как новая |
| Найдено несколько возможных совпадений | Система | Ожидает решения: выбор из списка |
| Пустая дата заполнения (пример 15) | Не ошибка | `date_filled` не задано, учебный год — по дате загрузки, с отметкой в предпросмотре |
| Дата `7.10.2026` (пример 17) | Ошибка `check()` | Как любая ошибка даты: к возврату. Извлечённый JSON сохраняется в `extracted`, хотя он не проходит JSON Schema 2.0 ([вопрос 13](#142-открытые-вопросы)). Система не проверяет `extracted` по JSON Schema |

Предупреждения показываются у соответствующих полей предпросмотра, ошибки — в карточке загрузки и в тексте возврата. Всё сохраняется в загрузке.

### 7.5. Сопоставление с существующими записями

Сравнение выполняется по нормализованным значениям ([5.3](#53-правила-хранения-значений)).

**Преподаватель.**

1. Если ID анкеты есть среди выданных копий — преподаватель из копии. Если ФИО в анкете отличается от ФИО этого преподавателя, это предупреждение, а не повод сменить преподавателя.
2. Иначе — поиск по ФИО и кафедре. Совпадение ровно с одним — он. Совпадение ФИО без кафедры, совпадение только фамилии на той же кафедре или несколько совпадений — выбор ответственным.
3. Не найден — предложение создать. ФИО разбирается по пробелам: первое слово — фамилия, второе — имя, остальное — отчество. Инициалы («Иванов И. И.») разбираются так же; ответственный может исправить разбор. Это не исправление данных анкеты: ФИО преподавателя в справочнике задаёт ответственный.

**Кафедра.** Поиск по `name` и `aliases`. Новое написание существующей кафедры можно добавить в `aliases` из предпросмотра.

**Студент.**

1. Если ID анкеты уже есть у работы — студент этой работы ([7.6](#76-повторная-загрузка-той-же-анкеты)).
2. Иначе — поиск по ФИО и шифру группы, затем по email. Совпадение ровно с одним — он; изменившиеся контакты, курс или группа показываются как разница с предложением обновить.
3. Несколько совпадений или совпадение только по email при другом ФИО — выбор ответственным.
4. Не найден — создаётся новый.

Один студент может работать с несколькими преподавателями: это разные работы и разные анкеты. Это не дубликат.

**Группа.** Поиск по шифру без учёта регистра. Не найдена — создаётся при сохранении.

### 7.6. Повторная загрузка той же анкеты

Преподаватель может заполнять одну копию в течение года и присылать её несколько раз. Ключ — ID анкеты.

| Случай | Реакция |
| --- | --- |
| Тот же файл (совпал SHA-256) | «Дубликат файла», ничего не записывается. Если прежняя загрузка была возвращена, сообщение напоминает, что файл не исправлен |
| Тот же ID анкеты, другой файл, работа уже есть | Обновление существующей работы, а не новая работа. Предпросмотр показывает разницу по каждому полю. По умолчанию принимаются новые значения. Если поле после прошлой загрузки меняли вручную, оно отмечено, и ответственный выбирает, какое значение оставить |
| Тот же ID, что у возвращённой загрузки | Обрабатывается как новая анкета; при сохранении или новом возврате у возвращённой загрузки ставится ссылка `resubmission` |
| Тот же ID анкеты, но другой студент (иные ФИО и группа) | Предупреждение «анкета, вероятно, переиспользована для другого студента». Решение — за ответственным: обновить или отклонить. Создать новую работу с тем же ID нельзя |
| Дата заполнения новой анкеты раньше, чем у уже загруженной | Предупреждение «загружается более старая версия» |

**Достижения при обновлении.** Достижения сопоставляются по `source_row`. Строка с тем же номером — обновить текст. Новый номер — добавить. Номер, который был в прошлой анкете и пропал в новой, — достижение удаляется, но только после подтверждения в предпросмотре (в форме строку очищают, чтобы удалить достижение). Достижения, добавленные вручную (`source_row` пуст), не затрагиваются.

Каждая сохранённая загрузка становится ревизией в истории работы; исходные PDF всех ревизий доступны ответственным для скачивания.

### 7.7. Возврат анкеты преподавателю

Анкета с ошибками в системе не исправляется, а возвращается преподавателю (решение 4 в [14.1](#141-принятые-решения)). Интеграции с почтой для возврата нет: текст передаёт ответственный.

1. При обработке система формирует **текст возврата**:
   - ФИО студента (если удалось прочитать), ID анкеты, имя файла, дата загрузки;
   - список ошибок понятными словами и что исправить. Пример: «Электронная почта: неверный формат адреса. Укажите адрес полностью, например student@example.org»;
   - при отсутствии ID или старой версии формы — просьба перенести данные в новую копию формы, которую пришлёт ответственный;
   - напоминание: сохранять файл командой «Сохранить», а не «Печать в PDF», и прислать тот же файл после исправления.
2. На странице загрузки текст можно скопировать одной кнопкой или скачать как `.txt`. Для пакета — общий файл с текстами по всем анкетам к возврату, сгруппированный по преподавателям.
3. Передав текст, ответственный нажимает «Отмечено как возвращённое». Загрузка переходит в «Возвращено преподавателю», сохраняются `returned_by` и `returned_at`.
4. Исправленная анкета с тем же ID загружается обычным порядком и связывается с возвращённой (`resubmission`). Для анкеты без ID связь ставится через новую копию: копия, подготовленная из карточки возвращённой загрузки, хранит ссылку на неё.
5. Отчёт 8 «Сбор анкет» показывает возвращённые анкеты, по которым исправленная ещё не получена, и сколько дней прошло с возврата.

## 8. Подготовка копий формы

Функциональность `prepare_copy.py` в веб-интерфейсе. Решает две проблемы: пустые формы без ID (пример 20) и анкеты с пустым блоком преподавателя (пример 02). Копии готовят только ответственный и администратор (решение 2 в [14.1](#141-принятые-решения); [вопрос 19](#142-открытые-вопросы)).

- Администратор загружает пустую форму (PDF) как текущий шаблон; система проверяет, что это форма `prepod_vnok_info` поддерживаемой версии с пустым `student.id`.
- Ответственный выбирает преподавателя и, при желании, студентов или число копий. Система вызывает `prepare_copy()` (копия модуля, как в [7.3](#73-архитектура-импорта)) и получает PDF с новым ID и заполненными ФИО, должностью и кафедрой преподавателя.
- Каждая копия записывается в `IssuedCopy`. Файлы скачиваются по одному или ZIP-архивом. Имя файла — `Фамилия_И_О_<короткий ID>.pdf`.
- Из карточки загрузки «К возврату» без ID можно сразу подготовить копию для того же преподавателя; копия хранит ссылку на возвращённую загрузку.
- По выданным копиям строится отчёт о сборе ([9](#9-отчёты), отчёт 8).

## 9. Отчёты

Общие параметры всех отчётов: учебный год или произвольный период; кафедра (в пределах прав); включать ли неактивных студентов и неактивные работы ([5.4](#54-статусы-работы)). Период фильтрует работы по `academic_year` или по `date_filled`, достижения — по учебному году их работы.

Контактов студентов нет ни в одном отчёте, кроме отчёта 7 ([3.2](#32-где-скрываются-контакты)).

Форматы: просмотр в браузере (с сортировкой по столбцам), XLSX, CSV (UTF-8 с BOM, разделитель `;` — открывается в Excel без настройки), PDF (для печати и подписи). В шапке выгрузки — название отчёта, параметры, дата формирования, автор.

| № | Отчёт | Дополнительные фильтры | Столбцы | Форматы |
| --- | --- | --- | --- | --- |
| 1 | Карточка преподавателя | Преподаватель | ФИО, должность, кафедра; по каждой работе: студент, группа, курс, задача, статус, ожидаемые результаты, число достижений, перечень достижений, дата последней анкеты | HTML, PDF, XLSX |
| 2 | Сводка по кафедре | — | Преподаватель, должность, число активных студентов, число работ по каждому статусу (5 столбцов), число достижений в работах периода | HTML, XLSX, CSV, PDF |
| 3 | Студенты по курсам и группам | Курс, группа | Курс, группа, студент, преподаватель, тема (первая строка задачи), статус | HTML, XLSX, CSV |
| 4 | Работы по статусу | Статус (несколько), только активные | Статус, студент, группа, преподаватель, комментарий к статусу, дата последнего обновления; итоги по статусам | HTML, XLSX, CSV |
| 5 | Достижения за учебный год | Учебный год, преподаватель | Текст, студент, группа, преподаватель, кафедра, учебный год работы; итоги по преподавателям | HTML, XLSX, CSV, PDF |
| 6 | Нагрузка преподавателей | Минимальное число студентов | Преподаватель, кафедра, число активных студентов, число работ, из них завершённых; сортировка по убыванию числа студентов | HTML, XLSX, CSV |
| 7 | Контакты студентов преподавателя | Преподаватель | Студент, группа, телефон, email. Только для ответственных; каждый просмотр и выгрузка записываются в журнал аудита | HTML, XLSX |
| 8 | Сбор анкет | Состояние | Выдано копий, получено, ожидает решения, к возврату, возвращено и не получено повторно, отклонено; по каждой копии: преподаватель, студент, дата выдачи, дата последней загрузки, состояние; по каждой возвращённой анкете: преподаватель, студент, дата возврата, дней с возврата | HTML, XLSX |
| 9 | Качество данных | — | Работы без достижений, без расписания, без даты; анкеты, не обновлявшиеся дольше N дней (по умолчанию 90); импорт с предупреждениями; возможные дубликаты студентов | HTML, XLSX |
| 10 | Журнал импорта | Пакет, автор, состояние, период | Дата, автор, файл, ID анкеты, состояние, ошибки и предупреждения, ссылка на работу. Только ответственным и администратору | HTML, CSV |

Формирование любого отчёта на объёме из [11.4](#114-объём-данных-и-производительность) — не дольше 5 секунд для HTML и 30 секунд для выгрузки.

| `EXPORT_SYNC_ROWS` | Выгрузка в JSON без файлов и не больше этого числа записей выполняется сразу, иначе — в фоне |
| `TLS_CERT_PATH`, `TLS_KEY_PATH` | Сертификат для nginx |

Порядок запуска `web`: ожидание БД → `migrate` → `collectstatic` → создание администратора, если заданы переменные `DJANGO_SUPERUSER_*` и такого пользователя нет → gunicorn. Миграции применяются автоматически; откат — вручную по инструкции.

Первый запуск — три команды: скопировать `.env.example` в `.env` и заполнить, `docker compose up -d`, открыть сайт. Создать администратора без переменных: `docker compose exec web python manage.py createsuperuser`.

Для разработки — `compose.override.yaml`: `DEBUG=1`, монтирование исходников, `runserver`, без nginx.

Резервное копирование: скрипт `scripts/backup.sh` делает `pg_dump` в формате custom и архив тома `media` с меткой времени; `scripts/restore.sh` восстанавливает. Расписание запуска (cron на хосте) и место хранения копий определяет заказчик. Восстановление проверяется на приёмке.

### 11.3. Безопасность и персональные данные

Система обрабатывает персональные данные: ФИО, телефоны, адреса почты студентов, ФИО и должности преподавателей. Требования законодательства о персональных данных (152-ФЗ), включая согласия субъектов и уровень защищённости, определяет заказчик ([вопрос 10](#142-открытые-вопросы)). Со стороны системы:

- доступ только после входа; разграничение по ролям и кафедрам на сервере ([3.1](#31-права));
- телефон и email студента видят только ответственные, во всех представлениях, выгрузках и API ([3.2](#32-где-скрываются-контакты));
- HTTPS; cookie `Secure`, `HttpOnly`, `SameSite=Lax`; стандартные защиты Django (CSRF, XSS, clickjacking);
- пароли — стандартные хешеры Django, требования к сложности; блокировка после 10 неудачных попыток входа на 15 минут;
- загруженные PDF не раздаются напрямую из `media`: скачивание только через представление с проверкой прав;
- PDF разбирается только `pypdf`, без выполнения JavaScript из файла. Проверка MIME-типа и сигнатуры `%PDF`, ограничения размера, распаковка ZIP с защитой от «zip-бомб» и путей вида `../`;
- в журналах приложения нет телефонов, email и текстов анкет — только идентификаторы;
- смена пользователя — только через выход и вход с паролем; вход «под другим пользователем» без пароля не предусмотрен;
- журнал аудита: вход, выход (при смене пользователя — с признаком), неудачный вход, импорт, подтверждение, отклонение и возврат, смена статуса, удаление, объединение записей, просмотр и выгрузка отчёта с контактами, скачивание PDF;
- срок хранения исходных PDF и порядок удаления данных выпускников определяет заказчик; в системе — команда удаления исходных PDF старше заданного срока с сохранением извлечённых данных.

### 11.7. Выгрузка базы в JSON

Назначение: систему будут дорабатывать, и при переработке структура базы может сильно измениться. Нужен полный снимок данных, понятный без исходного кода, пригодный для долгого хранения, чтения другими программами и загрузки обратно — в эту же версию системы или, через преобразование, в следующую. Резервное копирование (`scripts/backup.sh`, [11.2](#112-развёртывание-через-docker-compose)) выгрузка не заменяет.

Состав: все данные предметной области (кафедры, преподаватели, группы, студенты, работы, достижения, статусы), история изменений (`django-simple-history`), пакеты и загрузки импорта с извлечёнными данными и результатами проверки, шаблоны формы, выданные копии, пользователи с хешами паролей, роли, токены API, журнал аудита. Не выгружаются служебные таблицы Django (типы содержимого, права, группы, сеансы, журнал админ-панели) и данные блокировки входа. Файлы (PDF) в JSON представлены путём, размером и SHA-256; сами файлы — по выбору в том же архиве.

Формат — собственный, «таблица → записи», описан в [doc/json-format.md](json-format.md):

- один ZIP-архив: `manifest.json` (заголовок), `data/<таблица>.json`, при выгрузке с файлами — `media/`;
- заголовок: версия формата, версия системы, последние миграции, время, кто выгрузил, число записей и SHA-256 каждой таблицы, контрольная сумма, схема (поля, типы, ссылки, перечни значений);
- ссылки — по первичным ключам, у основных сущностей — человекочитаемый ключ `_key`;
- даты и время — ISO 8601 (UTC), UTF-8 без экранирования кириллицы, записи по возрастанию ключа, по одной в строке: две выгрузки одной базы сравниваются построчно;
- запись и чтение потоком, база в память целиком не загружается.

Восстановление:

- только в пустую базу после `migrate`; уже созданные пользователи удаляются только по явному ключу; режима замены текущих данных нет — порядок замены описан в руководстве администратора;
- до записи — полная проверка без изменения базы (её же выполняет режим `--dry-run`): целостность архива и контрольные суммы, версия формата, миграции базы, состав полей, типы, обязательные поля, уникальность, ссылки, пути файлов;
- выгрузка более старого формата проходит через цепочку преобразований «версия N → N+1»; выгрузка более новой версии отклоняется. Изменение моделей без новой версии формата обнаруживает автотест;
- всё в одной транзакции, затем установка последовательностей ключей; записи истории и аудита от имени восстановления не создаются, кроме одного события «восстановление из JSON»;
- отчёт: число записей по таблицам в сравнении с заголовком; файлы восстановленные, отсутствующие и с несовпавшей SHA-256. Восстановление без файлов допустимо.

Интерфейс и права: команды `export_json` и `restore_json`; страница «Администрирование → Выгрузка в JSON» — только суперпользователю, большая выгрузка выполняется обработчиком `worker`. Восстановление — только командой. Архивы на сервере хранятся вне `media` (том `exports`) и отдаются только через проверку прав. Выгрузка, скачивание, удаление архива и восстановление записываются в журнал аудита. Архив содержит контакты студентов — исключение из [3.2](#32-где-скрываются-контакты), см. [вопрос 21](#142-открытые-вопросы).

## 12. Тестирование и приёмка

### 12.1. Автоматические тесты

- Модель и проверки: обязательные поля, email, дата, курс, уникальность `questionnaire_id`, переходы статусов.
- Права: для каждой роли — доступ к спискам, карточкам, выгрузкам, API и файлам в своей и чужой области; отсутствие контактов студентов везде, кроме представлений для ответственных ([3.2](#32-где-скрываются-контакты)). Смена пользователя для каждой роли; доступ к админке Django: есть у суперпользователя и роли «Администратор», нет у остальных.
- Выгрузка в JSON ([11.7](#117-выгрузка-базы-в-json)): выгрузка → пустая база → восстановление → повторная выгрузка совпадает с первой; отказ на непустой базе, повреждённом архиве, неверной контрольной сумме, более новой версии формата, битой ссылке; восстановление без файлов; последовательности ключей; права на страницу выгрузки.
- Импорт: все 20 примеров `examples/` — копируются в тестовые данные проекта (с указанием источника) и прогоняются через импорт с ожиданиями из таблицы 12.2.
- Паритет адаптера с `extract_static.py`: извлечённые данные и сообщения на 20 примерах совпадают с описанными в `examples/README.md`.
- Повторная загрузка: тот же файл; тот же ID с изменёнными полями; удалённое и добавленное достижение; ручная правка между загрузками; исправленная анкета после возврата.
- Возврат: текст возврата содержит все ошибки; отметка возврата; связь с повторно присланной анкетой.
- Отчёты: на наборе примеров числа в отчётах 2, 5, 6, 8 совпадают с подсчитанными вручную.
- Развёртывание: сборка образа и запуск `docker compose up` на чистой машине, `/health/` отвечает.

| 9 | Одна система на кафедру или на вуз? Нужна ли структура выше кафедры (факультет, институт)? | Кафедра — верхний уровень; факультет можно добавить позже |
| 10 | Требования по персональным данным: уровень защищённости, согласия, срок хранения PDF | Срок хранения не ограничен до решения; команда удаления старых PDF есть |
| 11 | Ожидаемый объём: число кафедр, преподавателей, студентов, анкет в год? | См. [11.4](#114-объём-данных-и-производительность) |
| 12 | Нужна ли интеграция с внешними системами: кадровой, учебной, LDAP/AD, почтой? | LDAP и почтовые уведомления ответственным — этап 3, отключены по умолчанию |
| 13 | Пример 17: JSON с датой `7.10.2026` не проходит JSON Schema 2.0. Что исправлять в проекте формы: шаблон схемы или поведение извлечения? | Система не проверяет JSON по схеме; анкета возвращается из-за ошибки даты |
| 14 | Как разделять студентов и курсантов, нужно ли это в отчётах? | Необязательное поле «категория», не заполняется из анкеты |
| 15 | Где будет размещена система: закрытая сеть без интернета, свой сервер, требования к ОС и сертификатам? | Закрытая сеть возможна: без CDN и внешних обращений; сертификат предоставляет заказчик |
| 16 | Как считать учебный год и закрывать работы по его окончании? | Учебный год с 1 сентября; работы не закрываются автоматически, отчёт 9 показывает давно не обновлявшиеся |
| 17 | Нужно ли преподавателю что-то менять в системе самому (например, статус работы)? Сейчас он только смотрит свои работы | Только просмотр; все изменения — через анкету и ответственного |
| 18 | Заменить в следующей версии формы текстовое поле «Текущий статус» списком из [5.4](#54-статусы-работы)? Это изменение проекта формы | Предлагается. До этого статус выбирает ответственный при импорте |
| 19 | Нужно ли преподавателю самому готовить копии формы для своих студентов? | Нет, копии готовит ответственный |
| 20 | Должен ли администратор видеть контакты студентов? По решению 6 — нет, но администратор имеет доступ к базе данных и резервным копиям | В интерфейсе — нет, если нет роли ответственного; доступ к базе регулируется организационно |
| 21 | Полная выгрузка в JSON ([11.7](#117-выгрузка-базы-в-json)) содержит контакты студентов и хеши паролей, а делает её суперпользователь, у которого может не быть роли ответственного. Допустимо ли это, или нужен вариант выгрузки без контактов (для передачи данных разработчикам)? | Выгрузка полная, только для суперпользователя, с предупреждением и записью в аудит — как доступ к резервным копиям ([вопрос 20](#142-открытые-вопросы)). Вариант без контактов не делается: такой снимок нельзя восстановить |

## 15. Риски

| Риск | Последствие | Мера |
| --- | --- | --- |
| Форма не утверждена, состав полей изменится | Переделка импорта и модели | Адаптеры по версиям схемы, хранение исходного JSON, нейтральная структура импорта ([7.3](#73-архитектура-импорта)) |
| Форма проверена только в Firefox; поведение Acrobat и других программ неизвестно (в том числе отображение ISO-даты) | Появятся новые варианты значений в PDF | Проверки и предпросмотр показывают любые неожиданные значения; новые случаи добавляются в тестовый набор |
| Копия `extract_static.py` разойдётся с проектом форм | Разное поведение проверки в форме и в системе | Тест паритета на примерах; SHA-256 копии в README модуля; переход на пакет (вариант В) |
| Анкеты без ID и без данных преподавателя | Дубликаты и неверная привязка | Выдача копий через систему (раздел 8), возврат анкет без ID, обязательный предпросмотр, отчёт 9 о возможных дубликатах |
| Много возвратов из-за мелких ошибок (пробел в email, дата без ведущего нуля) | Задержка сбора данных | Понятный текст возврата; отчёт 8 с анкетами, ожидающими исправления; предложение проверять анкету перед отправкой |
| Свободный текст статуса в форме | Ответственный выбирает статус вручную при каждом импорте | Фиксированный список статусов ([5.4](#54-статусы-работы)); список в следующей версии формы ([вопрос 18](#142-открытые-вопросы)) |
| Неопределённость требований по персональным данным | Доработки перед вводом в эксплуатацию | Разграничение прав, скрытие контактов, аудит, HTTPS с первого этапа; [вопрос 10](#142-открытые-вопросы) |
| Архив выгрузки в JSON попадёт к посторонним: в нём все персональные данные и хеши паролей | Утечка персональных данных | Выгрузка только суперпользователю, архивы вне `media`, аудит выгрузки и скачивания, предупреждение на странице; хранение и передача — как у резервных копий ([11.7](#117-выгрузка-базы-в-json), [вопрос 21](#142-открытые-вопросы)) |
| Переработка системы изменит модели, а старые выгрузки перестанут читаться | Потеря возможности перенести данные | Версия формата, сохранённые схемы всех версий, цепочка преобразований, автотест на изменение моделей ([doc/json-format.md](json-format.md#8-версии-формата-и-преобразование)) |
