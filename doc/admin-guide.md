# Руководство администратора

Система «Учёт НИР», требования — [tz.md](tz.md). Команды выполняются из каталога проекта.

## 1. Установка

Подробно — с настройкой сертификата, проверкой, обновлением, установкой без интернета и разбором типичных проблем — в [руководстве по развёртыванию](deployment.md).

Требования к серверу: Linux с Docker Engine 24+ и Docker Compose v2, 2 ГБ памяти, место под базу данных и PDF (расчёт — ТЗ 11.4: около 25 ГБ на 50 000 загрузок). Доступ в интернет нужен только для сборки образов; работающая система внешних ресурсов не использует.

1. Скопировать проект на сервер.
2. `cp .env.example .env` и заполнить:
   - `DJANGO_SECRET_KEY` — длинная случайная строка, например `python3 -c "import secrets; print(secrets.token_urlsafe(48))"`;
   - `POSTGRES_PASSWORD`;
   - `DJANGO_ALLOWED_HOSTS` и `DJANGO_CSRF_TRUSTED_ORIGINS` — имя сервера; в `DJANGO_CSRF_TRUSTED_ORIGINS` — полный адрес со схемой и портом, если он не 443: `https://nir.example.org:8443`;
   - `SERVER_NAME`, `HTTP_PORT`, `HTTPS_PORT`;
   - `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_PASSWORD` — первый администратор (можно не задавать и создать позже).
3. Сертификат: положить `server.crt` и `server.key` в каталог `TLS_CERT_DIR` (по умолчанию `docker/certs/`). Если файлов нет, при запуске создаётся самоподписанный сертификат на год — только для проверки.
4. `docker compose up -d --build`.
5. Проверить: `curl -k https://localhost:$HTTPS_PORT/health/` → `{"status": "ok", "database": true, "storage": true}`.

Администратора без переменных окружения: `docker compose exec web python manage.py createsuperuser`.

### Сервисы и тома

| Сервис | Назначение |
| --- | --- |
| `db` | PostgreSQL 17, том `pgdata` |
| `web` | Django + gunicorn. При запуске: ожидание БД, `migrate`, `collectstatic`, создание администратора из `DJANGO_SUPERUSER_*` |
| `worker` | Фоновая обработка пакетов больше `IMPORT_SYNC_LIMIT` файлов и больших выгрузок в JSON; уведомления (`NOTIFY_PENDING_HOURS`) |
| `nginx` | HTTPS, статика, перенаправление с HTTP |

Тома: `pgdata` (база), `media` (загруженные PDF, выданные копии, шаблон формы), `exports` (архивы выгрузки в JSON, [раздел 8](#8-выгрузка-в-json-и-восстановление)), `static` (пересобирается при запуске). Файлы из `media` отдаются только через приложение с проверкой прав — nginx их не публикует.

## 2. Пользователи и роли

«Администрирование → Пользователи, роли, настройки» (админ-панель Django, `/admin/`). В карточке пользователя — блок «Роли»:

| Роль | Кафедра | Что даёт |
| --- | --- | --- |
| Администратор | пусто | Вся система, кроме контактов студентов |
| Ответственный кафедры | кафедра или пусто (все) | Ввод данных, импорт, возврат, копии, контакты студентов своей области |
| Наблюдатель | кафедра или пусто (все) | Просмотр и отчёты без контактов |

Роль «Преподаватель» — это связь: в карточке преподавателя (в интерфейсе, «Преподаватели → Изменить», поле «Учётная запись») выбрать пользователя. Преподаватель видит только свои работы, без контактов студентов.

Суперпользователь Django — администратор системы. Чтобы администратор видел контакты, ему нужна ещё и роль ответственного (ТЗ 3.2, вопрос 20).

Новую кафедру создаёт администратор («Справочники → Кафедры»). Ответственный с областью «все кафедры» тоже может создать кафедру из предпросмотра импорта.

### Токены API

`/admin/authtoken/tokenproxy/` → «Добавить», выбрать пользователя. Запросы: `curl -H "Authorization: Token <ключ>" https://сервер/api/works/`. API отдаёт данные в правах этого пользователя. Ресурсы: `departments`, `groups`, `teachers`, `students`, `works` (фильтры `teacher`, `student`, `status`, `academic_year`, `department`).

### Вход через LDAP / Active Directory

В `.env`: `LDAP_ENABLED=1`, `LDAP_SERVER_URI`, затем один из режимов:

- шаблон DN: `LDAP_USER_DN_TEMPLATE=uid={username},ou=people,dc=example,dc=org` (для AD — `{username}@example.org`);
- поиск: `LDAP_BIND_DN`, `LDAP_BIND_PASSWORD`, `LDAP_SEARCH_BASE`, `LDAP_SEARCH_FILTER` (для AD — `(sAMAccountName={username})`).

При первом входе создаётся локальная учётная запись без пароля; ФИО и почта берутся из атрибутов `LDAP_ATTR_*`. Роли назначает администратор. Локальные учётные записи продолжают работать.

## 3. Шаблон формы

«Импорт → Шаблон формы» — загрузить пустую форму `prepod_vnok_info` версии 2.0 (сейчас `prepod_vnok_info-v2.0-draft04.pdf` из проекта формы). Система проверяет, что это поддерживаемая форма без ID анкеты. Текущий шаблон используется для всех новых копий.

## 4. Резервное копирование и восстановление

```bash
scripts/backup.sh /путь/к/резервным/копиям      # db-ДАТА.dump (pg_dump -Fc) и media-ДАТА.tar.gz
scripts/restore.sh /путь/db-ДАТА.dump /путь/media-ДАТА.tar.gz
```

`restore.sh` останавливает приложение, **заменяет** данные базы и файлы, запускает всё снова. Расписание копирования — cron на сервере, например ежедневно в 02:00:

```cron
0 2 * * * cd /opt/stocktaking && scripts/backup.sh /backup/stocktaking >> /var/log/stocktaking-backup.log 2>&1
```

Храните копии вне сервера. Резервные копии содержат персональные данные студентов.

## 5. Обновление

```bash
scripts/backup.sh /backup/stocktaking
git pull                      # или скопировать новую версию
docker compose up -d --build  # миграции применяются при запуске web
```

Откат миграций — вручную: `docker compose exec web python manage.py migrate <приложение> <миграция>`, затем запустить предыдущую версию образа. Надёжнее — восстановить резервную копию.

## 6. Обслуживание

| Задача | Команда |
| --- | --- |
| Журналы | `docker compose logs -f web worker` |
| Удалить исходные PDF старше N дней (данные остаются) | `docker compose exec web python manage.py purge_pdfs --older-than-days 1095 [--dry-run]` |
| Разослать уведомления ответственным сейчас | `docker compose exec web python manage.py notify_pending` |
| Обработать очередь импорта вручную | `docker compose exec web python manage.py run_worker --once` |
| Журнал аудита | «Администрирование → Журнал аудита» |

Уведомления по почте: задать `EMAIL_HOST` и соседние переменные, `SITE_URL` и `NOTIFY_PENDING_HOURS` (например, 24). Письма содержат только число загрузок и ссылку, без данных студентов.

## 7. Обновление копии модулей формы

Если в проекте формы изменились `extract_static.py`, `acroform.py` или `prepare_copy.py`, — порядок в [imports/adapters/prepod_vnok_info_v2/vendor/README.md](../imports/adapters/prepod_vnok_info_v2/vendor/README.md). Новая версия схемы данных — новый адаптер; анкеты в состоянии «Версия не поддерживается» после этого обрабатываются заново кнопкой в карточке загрузки.

## 8. Выгрузка в JSON и восстановление

Полный снимок базы в ZIP-архиве с JSON: справочники, работы, достижения, история изменений, загрузки PDF с извлечёнными данными, выданные копии, шаблоны формы, пользователи с хешами паролей, роли, токены API, журнал аудита. По желанию — вместе с самими PDF. Формат описан в [json-format.md](json-format.md) так, чтобы выгрузку можно было прочитать без кода системы.

| | `scripts/backup.sh` (pg_dump) | Выгрузка в JSON |
| --- | --- | --- |
| Назначение | Ежедневное резервное копирование и аварийное восстановление | Перенос данных, архив перед переработкой системы, передача данных другой программе |
| Куда восстанавливается | Только в ту же версию PostgreSQL и системы | В эту же версию системы или, через преобразование формата, в более новую; база может быть PostgreSQL или SQLite |
| Читается без системы | Нет | Да, формат описан |
| Восстановление | Заменяет текущие данные | Только в пустую базу, с полной проверкой до записи |

Выгрузка в JSON резервное копирование не заменяет: продолжайте запускать `backup.sh` по расписанию.

> **Архив содержит персональные данные студентов** (ФИО, телефоны, email — в записях и в PDF), **хеши паролей и действующие ключи API.** Храните и передавайте его так же, как резервные копии, только по защищённым каналам. Ненужные архивы удаляйте с сервера. Каждая выгрузка, скачивание, удаление архива и восстановление записываются в журнал аудита (`json_export`, `json_export_download`, `json_export_delete`, `json_restore`).

### 8.1. Выгрузка через интерфейс

«Администрирование → Выгрузка в JSON» — только для суперпользователя (роль «Администратор» без флага суперпользователя этого пункта не видит).

1. Отметить «Включить файлы», если нужны PDF.
2. «Выгрузить». База без файлов и не больше `EXPORT_SYNC_ROWS` записей (по умолчанию 5000) выгружается сразу. Иначе выгрузка уходит в фон (`worker`), и страница обновляется сама, пока выгрузка не закончится.
3. «Скачать». Архивы лежат на сервере в томе `exports` (`/data/exports` в контейнерах), отдельно от `media`, и отдаются только суперпользователю. «Удалить» убирает архив с сервера.

Если выгрузка осталась «Выполняется» после перезапуска `worker`, она прервалась: удалите запись и запустите выгрузку снова.

### 8.2. Выгрузка командой

```bash
docker compose exec web python manage.py export_json                          # → /data/exports/stocktaking-ДАТА.zip
docker compose exec web python manage.py export_json /data/exports/full.zip --with-media
docker compose cp web:/data/exports/full.zip /backup/stocktaking/               # забрать архив с сервера
```

Команда печатает число записей по таблицам, число файлов и предупреждения. Выгрузка читает базу одним согласованным снимком (PostgreSQL, `REPEATABLE READ`): работать с системой во время выгрузки можно. Ориентир по времени — на объёме из ТЗ 11.4 (20 000 работ, 50 000 загрузок, около 130 000 записей) выгрузка без файлов занимает 5 секунд, архив — 2,5 МБ; с файлами время и размер определяются объёмом PDF.

### 8.3. Восстановление

Только командой и только в пустую базу: восстановление поверх данных не выполняется.

1. Развернуть систему той же или более новой версии ([deployment.md](deployment.md)) с пустой базой. `web` при запуске применит миграции. Если в `.env` заданы `DJANGO_SUPERUSER_*`, будет создан администратор: его заменят пользователи из выгрузки (ключ `--drop-existing-users` ниже).
2. Скопировать архив в контейнер:
   ```bash
   docker compose cp full.zip web:/tmp/full.zip
   ```
3. Проверить, ничего не меняя:
   ```bash
   docker compose exec web python manage.py restore_json /tmp/full.zip --dry-run --drop-existing-users
   ```
   Отчёт: заголовок выгрузки, число записей по таблицам, файлы (будет восстановлено, уже на месте, отсутствуют, не совпала SHA-256), предупреждения и ошибки. При ошибках команда завершается с кодом 1.
4. Восстановить:
   ```bash
   docker compose exec web python manage.py restore_json /tmp/full.zip --drop-existing-users
   docker compose exec web rm /tmp/full.zip
   ```
   Всё загружается в одной транзакции: при ошибке база остаётся пустой. Пароли пользователей — те же, что в исходной системе.
5. Проверить: вход, списки работ, отчёты, скачивание PDF.

Восстановление без файлов (архив без `media/`) допустимо: записи загружаются, файлы показываются в отчёте как отсутствующие, а их скачивание отвечает «не найдено». Если файлы перенесены отдельно (например, архивом тома `media` из `backup.sh`) и лежат в `/data/media` до восстановления, они считаются «уже на месте» после сверки SHA-256.

**Заменить текущие данные выгрузкой.** Отдельного режима нет: замена — это потеря текущих данных, и она должна быть явным действием. Порядок:

```bash
scripts/backup.sh /backup/stocktaking                                     # резервная копия текущего состояния
docker compose exec web python manage.py export_json /data/exports/before-replace.zip --with-media
docker compose stop worker
docker compose exec web python manage.py flush --no-input                 # удаляет ВСЕ данные базы
docker compose exec web sh -c 'find /data/media -mindepth 1 -delete'     # если в выгрузке есть файлы
docker compose exec web python manage.py restore_json /tmp/full.zip
docker compose start worker
```

Типичные отказы:

| Сообщение | Что делать |
| --- | --- |
| «База не пустая» | Восстанавливать в новую базу или очистить текущую (см. выше) |
| «В базе уже есть пользователи» | Добавить `--drop-existing-users` |
| «В базе применены не все миграции» | `docker compose exec web python manage.py migrate` |
| «Выгрузка сделана более новой версией системы» | Обновить систему до версии не ниже `app_version` из отчёта |
| «SHA-256 не совпадает», «Контрольная сумма» | Архив повреждён при копировании: взять другую копию |
| «Файл … уже есть в MEDIA_ROOT с другим содержимым» | В `/data/media` остались чужие файлы: очистить каталог |
